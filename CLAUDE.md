# CLAUDE.md

Guidance for Claude Code (or any AI coding agent) working in this repository.

## What this is

A monorepo for PulseQueue — positioned as **notification infrastructure**, not a notification CRUD app: any producer with a valid API key hands off a `DomainEvent` (e.g. `expense.created`, `donation.created`) onto a RabbitMQ topic exchange and PulseQueue owns everything from there — queueing, retry with backoff, dead-lettering, Redis-backed dedup, per-source rate limiting, and fan-out to Email (real SMTP), Push (simulated) and WebSocket (real) — while every outcome (processed, failed, retried, dead-lettered, duplicate) is persisted to Postgres and surfaced on a live, Kibana-style dark dashboard, polling REST stats and subscribing to a STOMP topic for real-time events. Renamed from EventFlow to PulseQueue to make that infrastructure framing explicit — see the root README's architecture section for the pitch.

```
pulsequeue/
├── backend/    Spring Boot 3 API (Java 21, RabbitMQ, Redis, PostgreSQL/Flyway, WebSocket/STOMP)
├── frontend/   React + TypeScript dashboard (Vite, Tailwind, TanStack Query, STOMP.js)
├── monitoring/ Prometheus scrape config + Grafana provisioning (datasource + one dashboard)
├── docker-compose.yml   Orchestrates db + rabbitmq + redis + api + web + prometheus + grafana
└── .github/workflows/ci.yml   backend (Maven+Testcontainers) + frontend (npm) jobs
```

**No longer fully standalone as of the PulseHub bridge (below).** It still exposes `POST /api/v1/events` and `/api/v1/events/simulate` to publish sample events itself, rather than being called by CashPilot/Social Supply, and don't add further cross-repo integration code beyond what's documented here without asking again — but `PulseHubNotificationChannel` (explicitly requested) does call back to PulseHub over HTTP. See "The PulseHub bridge" below before touching that channel or the `institution_mapping` table.

### The PulseHub bridge

`PulseHubNotificationChannel` (`notification/`) turns a `DomainEvent` into a real chat message in PulseHub: if the event's `payload` carries both `targetInstitutionId` (number) and `message` (string), `targetsFor` looks up `institution_mapping` (`entity/InstitutionMapping.java`, `repository/InstitutionMappingRepository.java`, migration `V2__create_institution_mapping.sql`) and returns that institution's `pulsehubUserId` as the single target; `send` then `POST`s `{targetUserId, content}` to PulseHub's `POST /api/v1/system-messages` with an `X-API-Key` header (`pulsequeue.pulsehub.api-key`, env `PULSEHUB_API_KEY` — must match PulseHub's `SYSTEM_API_KEY`). Any other event (no `targetInstitutionId`/`message`, or no mapping row for that institution) has no target, so the channel is never sent. **It is the one best-effort channel** (`isBestEffort()` returns `true`): `send` throws on failure like every other channel, and `NotificationDispatchService` records the failure and logs it instead of failing the event — an unreachable PulseHub instance must not turn an unrelated event into a retry/DLQ entry, so don't flip that flag to "fix" a swallowed exception.

`institution_mapping` (`institution_id` unique → `pulsehub_user_id`) is managed via `POST`/`GET /api/v1/institution-mappings` (`InstitutionMappingController`) — `permitAll()`, same as the rest of this dashboard-facing API, not producer-only like `/api/v1/events`. There's no Social Supply-side trigger yet; test this end-to-end via `POST /api/v1/events` with a payload like `{"targetInstitutionId": 7, "message": "..."}`, or `/api/v1/events/simulate`-style manual testing.

**Known gap:** this repo's and PulseHub's `docker-compose.yml` are separate stacks with separate default networks — `pulsequeue.pulsehub.base-url` (env `PULSEHUB_BASE_URL`, default `http://localhost:8081`) assumes both are reachable from wherever PulseQueue's container runs, which requires either running both outside Docker, remapping ports, or joining the two compose networks explicitly. Nobody has wired that up yet.

## Running things

```bash
cd backend && ./mvnw -B clean test     # unit tests + Testcontainers integration test (needs Docker)
cd frontend && npm ci && npm run lint && npm run build   # or: npm run dev
```

Full stack via Docker (from repo root): `docker compose up --build` — dashboard at `:3000`, API at `:8080`, Swagger at `:8080/swagger-ui.html`, RabbitMQ management UI at `:15672` (pulsequeue/pulsequeue), Mailpit inbox at `:8027` (SMTP on `:1025`; 8025/8026 are taken by sibling projects on the dev machine), Prometheus at `:9090`, Grafana at `:3001` (admin/admin, anonymous viewer access also enabled).

**Environment note:** V1–V5 were built with no local JDK/Maven or Docker and verified only through GitHub Actions CI. Since V6 the backend suite runs locally through the Maven wrapper (`backend/mvnw`, no global Maven needed) against a local Docker daemon. Two things that bit the first local run on the Windows dev machine:

- Testcontainers must be 1.21.4 or newer: Docker Engine 29 rejects the older Docker API version that 1.20.x speaks (`Could not find a valid Docker environment`, HTTP 400).
- Lettuce/Netty could not open an NIO selector (`Unable to establish loopback connection` / `Invalid argument: connect`) because the JDK creates its selector wake-up socket in the user temp directory, which fails on that machine. It is machine-specific, so it is passed on the command line rather than committed to the pom: create `backend/target/uds` after `clean`, then run `./mvnw -B test "-DargLine=-Djdk.net.unixdomain.tmpdir=C:/Claudin/pulsequeue/backend/target/uds"`.

## The event pipeline

`DomainEvent` (`event/DomainEvent.java`) is a record: `eventId` (UUID, generated by `DomainEvent.of(...)`), `eventType`, `sourceService`, `payload` (a `Map<String, Object>`), `occurredAt`. `EventPublisher` publishes it to `pulsequeue.exchange` with the event's own `eventType` as the routing key; `pulsequeue.events.queue` is bound with `#` (catches everything) since there's a single processing pipeline, not per-type routing.

**Retry + Dead Letter Queue** (`config/RabbitMqConfig.java`): the main queue is declared with `x-dead-letter-exchange` pointing at `pulsequeue.exchange.dlx`. The listener container factory wraps `EventConsumer.onMessage` in a stateless `RetryOperationsInterceptor` (exponential backoff, `pulsequeue.retry.*` properties) that retries the *same delivery* in-process; once attempts are exhausted, `RejectAndDontRequeueRecoverer` rejects the message and RabbitMQ's dead-letter routing takes over automatically. `DeadLetterConsumer` listens on the DLQ purely to flip the corresponding `ProcessedEvent` row to `DEAD_LETTERED` — it's the *only* place that status is ever set.

**Deduplication is check-before / mark-after-success** (`service/DeduplicationService.java`), not claim-then-process. If the Redis key were claimed before dispatch, every in-process retry of a currently-failing delivery would see its own claim and get skipped as a "duplicate" instead of actually retrying. The key is only written once `NotificationDispatchService.dispatch(event)` succeeds — read the class javadoc before changing this, it's a real bug that was caught and fixed during initial development, not a stylistic choice.

**`ProcessedEvent`** (`entity/ProcessedEvent.java`) is upserted (found-or-created by `eventId`) on every delivery attempt, not just the final one — `retryCount` increments on each `markFailed` call, so the dashboard can show live retry counts while an event is still being retried, not just after it settles.

**Persistence for a failed attempt goes through `ProcessedEventRecorder`, a separate `@Transactional`-per-method bean — not a `@Transactional` `process()` method.** `EventProcessingService.process()` deliberately rethrows the triggering exception after recording a failure, so Spring AMQP's retry interceptor sees it and retries/eventually dead-letters the message. If `process()` itself were `@Transactional`, Spring would roll back *everything* written during that call — including the "this attempt failed" row — the instant the exception left the method, because that's what `@Transactional` rollback-on-uncaught-`RuntimeException` does. This was a real bug caught via CI: retries kept resetting `retryCount` to 1 instead of incrementing, and the row never actually existed by the time the DLQ consumer went looking for it (the "Event dead-lettered..." log line fired regardless, since it runs before the DB call — a log message is not proof a write happened). Calling through `ProcessedEventRecorder` (a distinct Spring-proxied bean, so each `find/recordProcessed/recordFailed/recordDuplicate` call is its own independently-committed transaction) fixed it. Don't move that logic back into one `@Transactional` method without re-solving this.

**Delivery is tracked per (event, channel, target)** in `notification_deliveries` (migration `V3`, `entity/NotificationDelivery.java`). A `NotificationChannel` no longer just "sends the event": `targetsFor(event)` lists the destinations it applies to (empty = channel does not apply) and `send(event, target)` delivers to one of them. `NotificationDispatchService` skips every pair already `DELIVERED` for that `eventId`, attempts all the rest even after one fails, and only then throws if a non-best-effort target failed. The point: a retry (and, later, a DLQ replay) resends only what failed, so one unreachable destination cannot cause the others to be notified two or three times. Rows are written through `DeliveryRecorder`, one committed transaction per call, for the same rollback reason as `ProcessedEventRecorder` above. `PulseQueueIntegrationTest.retryResendsOnlyTheDestinationThatFailed` proves this end to end with a channel that fails its first send. Targets must be stable across calls for the same event, since they are the tracking key.

**Email is real SMTP** (`EmailNotificationChannel`, `spring-boot-starter-mail`, `spring.mail.*` from `MAIL_HOST`/`MAIL_PORT`, sender from `pulsequeue.email.from`). It only applies when the payload has a non-blank string `recipientEmail`, which is also the delivery target; `/api/v1/events/simulate` includes one so the dashboard button produces visible mail. In Docker the SMTP server is Mailpit, a catch-all dev inbox — nothing leaves the machine. Unlike PulseHub it is **not** best-effort: an SMTP failure fails the event, so it retries and dead-letters. To see a real (not simulated) failure: `docker compose stop mailpit`, publish an event with a `recipientEmail`, and it lands in `DEAD_LETTERED` with the EMAIL delivery row `FAILED` after 3 attempts while PUSH/WEBSOCKET stay `DELIVERED` once. The mail starter also adds a `mail` component to `/actuator/health`, so the API reports `DOWN` while Mailpit is stopped — expected, not a bug. Push is still simulated (FCM/APNs need real credentials).

**Outbound webhooks** (`WebhookNotificationChannel`, `service/WebhookSubscriptionService`, `entity/WebhookSubscription`, migration `V4`): each active subscription whose `eventTypePattern` matches the event type (`*` = all, `expense.*` = prefix, otherwise exact) is one delivery target, keyed by subscription id. The event is `POST`ed as JSON with `X-PulseQueue-Signature: t=<unix seconds>,v1=<hex HMAC-SHA256(secret, "<t>." + raw body)>` (`WebhookSigner`), plus `X-PulseQueue-Event-Id` and `X-PulseQueue-Event-Type`. The body is serialized once and those exact bytes are both signed and sent — don't let the HTTP client re-serialize the object, or receivers can no longer verify it. A non-2xx answer or a timeout is a failed delivery: it fails the event (retry, then DLQ) and increments the subscription's `consecutive_failures`; at `pulsequeue.webhook.max-consecutive-failures` (default 10, counted per attempt, so roughly three events) the subscription is set inactive and stops being a target, which also unblocks the event currently retrying. A success resets the streak; `POST /api/v1/webhooks/{id}/enable` reactivates one.

- The secret is generated server-side (`whsec_` + 64 hex chars), stored in plain text because HMAC needs the raw value, and returned **only** in the `201` response of `POST /api/v1/webhooks`. `GET /api/v1/webhooks` never includes it.
- URL validation is scheme-only (absolute `http`/`https`). Private and loopback hosts are **not** blocked, so the API key holder can make this service call internal addresses (SSRF). That is deliberate for a demo whose receivers live on the Docker network; it would need an allowlist before any public deployment.
- `HttpClientConfig` registers a `RestClientCustomizer` that puts connect/read timeouts (`pulsequeue.webhook.connect-timeout-ms` / `read-timeout-ms`, 2s/5s) on every `RestClient` built from the auto-configured builder — that includes the PulseHub bridge. Deliveries run on the consumer thread, so a slow endpoint still delays the single pipeline by up to the read timeout per attempt; per-target retry queues are out of scope.
- There is no receiver in the compose stack. To try it, run any HTTP endpoint on the `pulsequeue_default` network and register its URL; `PulseQueueIntegrationTest`'s `WebhookReceiver` and the two `webhook*` tests show a receiver verifying the signature.

**Replaying a dead-lettered event** (`POST /api/v1/events/{eventId}/replay`, API key required, `service/EventReplayService`): `202` on success, `404` unknown event, `409` if it is not `DEAD_LETTERED`, `503` if RabbitMQ is unreachable. The original message no longer exists in RabbitMQ — `DeadLetterConsumer` acks it — so the event is rebuilt from its `processed_events` row (`payload`, plus `occurred_at` from migration `V5`; rows older than that column fall back to `received_at`) and republished with the **same `eventId`**. Same id is the whole point: delivery tracking then skips every destination already `DELIVERED` and retries only the failed ones, and dedup does not block it because its key is only written on success. Three things that are easy to break:

- The status change is one conditional `UPDATE ... WHERE status = 'DEAD_LETTERED'` (`ProcessedEventRepository.transition`), so two concurrent replay requests cannot both publish. Don't replace it with load-check-save.
- That claim is committed **before** publishing (through `ProcessedEventRecorder.claimForReplay`), so the consumer never reads the row half-changed; if publishing then fails, `releaseReplayClaim` puts it back to `DEAD_LETTERED` instead of leaving it stranded in `RECEIVED`.
- `retryCount` keeps accumulating across replays and `replayCount` counts the replays. Replaying an event whose payload has `simulateFailure: true` fails and dead-letters again — the flag is part of the event and is deliberately not stripped. To demo a replay that succeeds, use a real failure instead: stop Mailpit, publish an event with a `recipientEmail`, start Mailpit, replay.

**Simulating a failure deterministically:** `NotificationDispatchService.dispatch` throws immediately if `event.payload().get("simulateFailure") == true`, guaranteeing the event exhausts retries and lands on the DLQ. This is what the dashboard's "Simulate failure" button and `PulseQueueIntegrationTest`'s DLQ test both use — don't rely on random/flaky failures to exercise this path.

## Security

`ApiKeyAuthFilter` (`security/`) guards only the write endpoints — `POST /api/v1/events*` and any non-`GET` on `/api/v1/webhooks*` — everything else (dashboard reads, actuator, Swagger) is `permitAll()`. It's a plain `OncePerRequestFilter` checking a shared-secret `X-API-Key` header against `pulsequeue.security.api-key` (`API_KEY` env var), not a `UserDetailsService`/login flow — this is "only trusted producers can publish," not user auth, and there's deliberately no session, no JWT, no login screen. `SecurityConfig`'s `SecurityFilterChain` itself just `permitAll()`s everything and wires the filter in before `UsernamePasswordAuthenticationFilter`; the actual 401-and-short-circuit enforcement lives inside the filter, not in `authorizeHttpRequests(...)` rules. If you add a new write endpoint that should be producer-only, extend `ApiKeyAuthFilter.isProtected(...)`, don't bolt on a second auth mechanism. The frontend dashboard sends the same (documented-as-demo-only) dev key from `lib/api.ts` — it is the "trusted internal caller" for the Simulate buttons, not a model for how a real credential should reach a browser.

## Backend conventions (`backend/`)

- Package layout: `config` (RabbitMQ/WebSocket/typed `@ConfigurationProperties` records) → `event` (wire model) → `producer`/`consumer` → `notification` (channel fan-out) → `service` (dedup, rate limit, dashboard stats, orchestration) → `entity`/`repository` (Postgres) → `controller` (REST) → `metrics` (Micrometer).
- Config is typed, not `@Value`-injected: `RabbitMqProperties`, `RetryProperties`, `DedupProperties`, `RateLimitProperties`, `CacheProperties` are all `@ConfigurationProperties` records, enabled via `@ConfigurationPropertiesScan` on the main application class.
- Schema is owned by **Flyway** (`backend/src/main/resources/db/migration/V*.sql`), `ddl-auto: validate` — Hibernate never mutates the schema.
- Tests: JUnit 5 + Mockito unit tests per service with real branching logic (`EventProcessingServiceTest`, `NotificationDispatchServiceTest`, `RateLimitServiceTest`, `DeduplicationServiceTest`, `DashboardStatsServiceTest`), a `@WebMvcTest`+`spring-security-test` slice test for the API-key filter (`EventControllerSecurityTest`), `PulseHubNotificationChannelTest` (uses `MockRestServiceServer` bound to an injected `RestClient.Builder`, not a live PulseHub instance), plus one Testcontainers `PulseQueueIntegrationTest` proving the full pipeline against real Postgres/RabbitMQ/Redis (normal processing, retry-to-DLQ, duplicate-delivery, and retry-resends-only-what-failed paths — this one bypasses HTTP/security entirely by calling `EventPublisher` directly, and registers two test-only channels through a nested `@TestConfiguration`).
- API-key auth (see "Security" above) guards the publish endpoints only — there's still no user login/JWT, and that's intentional; don't add one unless asked.

## Frontend conventions (`frontend/`)

- Vite + React 18 + TypeScript, path alias `@/*` → `frontend/src/*`. No React Router — it's a single dashboard page, not a multi-page app.
- `src/hooks/useDashboardStats.ts` and `useRecentEvents.ts` poll REST via TanStack Query (`refetchInterval: 3000`); `useLiveNotifications.ts` is a plain `useEffect` + `@stomp/stompjs`/`sockjs-client` subscription to `/topic/notifications`, kept outside the query cache since it's a push feed, not a fetch-and-cache resource — same split PulseHub uses between TanStack Query and its socket state.
- `vite.config.ts` needs `define: { global: "window" }` — `sockjs-client` references Node's `global`, which doesn't exist in a browser; losing this breaks the app at import time.
- `src/vite-env.d.ts` (`/// <reference types="vite/client" />`) must exist for `import.meta.env.VITE_*` to type-check — easy to lose if the frontend is ever regenerated from scratch rather than edited in place.
- **Dark, Kibana-style theme is intentional, not a placeholder** — `tailwind.config.js`'s `canvas`/`panel`/`panelborder`/`muted`/`accent`/`status.*` tokens and `index.css`'s forced `color-scheme: dark` are the whole visual identity ("ops tool," not "admin CRUD panel"). Don't reintroduce light-mode/adaptive theming or swap back to generic `slate-*`/`white` Tailwind classes without discussing it — that was a deliberate pivot away from the original light dashboard.
- `StatsGrid.tsx` renders the six primary tiles in a fixed order (Messages Published, Messages Processed, Dead Letter Queue, Retry Queue, Consumers, RabbitMQ Status) plus a secondary row (Queue Depth, Failed Attempts, Duplicates Skipped) — that specific set and order is a deliberate product decision, not just "whatever fields the API returns," so don't reorder or drop tiles casually when the API shape changes.
- `lib/api.ts` attaches a demo `X-API-Key` header (`VITE_API_KEY`, default matching the backend's dev key) to every request via the shared axios instance — the backend only actually checks it on `POST /api/v1/events*`, so it's harmless on the GET-only dashboard/stats calls.

## Things to watch for

- If you add a new event type or notification channel, it flows through the *existing* `NotificationChannel` list (`List<NotificationChannel>` constructor-injected into `NotificationDispatchService` — Spring collects all beans of that type automatically). Add a new `@Component implements NotificationChannel` (`getChannelName`, `targetsFor`, `send`), don't touch the dispatch service itself — delivery tracking, skip-if-delivered and failure aggregation all come for free from the dispatcher.
- `AmqpAdmin.getQueueInfo(queueName)` (used by `DashboardStatsService` for queue depth **and** consumer count, via `QueueInformation.getMessageCount()`/`getConsumerCount()`) does a passive queue declare over AMQP — it does **not** need the RabbitMQ management HTTP API/plugin, unlike a naive implementation that calls the `:15672` management API directly. Don't "fix" this by adding an HTTP client to the management API; it would be strictly worse (extra network hop, extra auth, extra failure mode) for the same data.
- `rabbitMqStatus` in `DashboardStatsResponse` is derived from the *same* `AmqpAdmin.getQueueInfo(...)` call already used for queue depth/consumer count — if it throws, status is `"DOWN"`, else `"UP"` — rather than injecting Actuator's `RabbitHealthIndicator` bean directly. That was tried first and reverted: `RabbitHealthIndicator` isn't reliably available as a directly-autowirable bean in this Boot 3.3 auto-config chain (`NoSuchBeanDefinitionException` at context startup, caught by `PulseQueueIntegrationTest`), and deriving status from the admin call already in use is simpler and arguably more meaningful anyway (it's the exact call the rest of this service depends on working). Don't reintroduce the `RabbitHealthIndicator` dependency without re-solving why it wasn't found.
- The Grafana dashboard's panels only query metrics this service actually exposes (`pulsequeue_events_*` from `EventMetrics`, plus Micrometer's free `http_server_requests_seconds_count`). There is deliberately no RabbitMQ-specific Prometheus panel — that would need the `rabbitmq_prometheus` plugin enabled and a second scrape target, which isn't wired up. Queue depth is shown on the React dashboard instead (via `AmqpAdmin`), not Grafana.
